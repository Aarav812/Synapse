## 2024-05-18 - Prevent Unbounded Map Memory Leaks in Rate Limiters
**Vulnerability:** The Express in-memory rate limiter utilized a `Map` to track incoming requests per user/IP. The map grew unbounded because it created a new entry for every unique `userId` or `IP`. A maliciously crafted request storm using spoofed IPs or rotating user IDs would rapidly consume server memory, leading to an Out-Of-Memory (OOM) Denial of Service crash.
**Learning:** Even if entries are cleaned up periodically (e.g. via `setInterval` every 5 minutes), the rate of insertion during an attack can overwhelm memory before the cleanup loop triggers. Manually editing `package-lock.json` also causes CI failures, so dependency updates should be avoided or done strictly via package managers.
**Prevention:** Always impose a strict upper bound on the size of any in-memory caching or tracking structure. For ES6 `Map`, capping the size and evicting the oldest element (using `map.delete(map.keys().next().value)`) is a safe and effective O(1) mitigation for unbounded growth.
