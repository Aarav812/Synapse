## 2024-05-18 - Math.random() usage for sensitive identifiers
**Vulnerability:** The codebase was using `Math.random()` to generate unique identifiers (e.g., `generateId()`). `Math.random()` is not cryptographically secure, and its outputs can be predicted by an attacker, leading to ID collisions or predictability vulnerabilities.
**Learning:** This existed because `Math.random()` is convenient and built into older JavaScript environments, often used without considering the security implications in modern applications.
**Prevention:** Always use `window.crypto.randomUUID()` when available, or `window.crypto.getRandomValues()` as a secure fallback, for generating identifiers, tokens, or any random values where unpredictability is required.
## 2024-05-18 - XSS in dynamic chip rendering
**Vulnerability:** The codebase failed to escape `chip.icon`, `chip.title`, and `chip.description` when interpolating them into HTML within `btn.innerHTML = ...` in `frontend/js/chat_partial.js`. This allowed malicious payload execution via XSS if those chips were generated from user input or external APIs.
**Learning:** This existed because properties like `title` or `icon` might appear inherently safe, but when inserted directly into `innerHTML` using template literals, any payload (e.g. `<img src=x onerror=...`) will be executed by the browser.
**Prevention:** Always wrap dynamically interpolated values in an escaping function (like `escapeHtml()`) when constructing HTML strings for `innerHTML`, even for supposedly "safe" fields like titles or descriptions.
## 2025-02-18 - Fix DOMPurify config allowing XSS via data URI
**Vulnerability:** DOMPurify was configured with an `ALLOWED_URI_REGEXP` override that permitted `data:` URIs globally. This allowed malicious payloads like `<a href="data:text/html;base64,...">` to execute arbitrary scripts via XSS, bypassing DOMPurify's default restrictions.
**Learning:** The configuration was added under the mistaken belief it was necessary to permit `data:` URIs for base64 images generated by the AI (e.g. `<img src="data:image/jpeg;base64,...">`). In reality, DOMPurify natively allows `data:` URIs on safe attributes like `src` while stripping them from dangerous ones like `href`.
**Prevention:** Do not override security-critical library configurations (like `ALLOWED_URI_REGEXP` in DOMPurify) without first consulting their default behaviors, as doing so often inadvertently broadens the attack surface unnecessarily.
## 2025-02-18 - XSS via allow-same-origin in sandboxed iframe
**Vulnerability:** The AI artifact preview iframe (`code-preview-iframe`) included the `allow-same-origin` sandbox directive. This permitted arbitrary, untrusted HTML generated by the AI (or injected via a shared chat URL) to execute JavaScript in the same origin context as the main application, granting full access to `localStorage`, IndexedDB, and Firebase sessions.
**Learning:** This existed because `allow-same-origin` is frequently added to iframes alongside `allow-scripts` out of habit, or to make certain scripts work without realizing that combining the two on an iframe hosting untrusted content completely defeats the sandbox, turning it into a severe XSS vector.
**Prevention:** Never use `allow-same-origin` together with `allow-scripts` on an iframe intended to safely host untrusted or user-generated HTML. Omitting `allow-same-origin` forces the iframe into an opaque origin, isolating it safely while still allowing scripts to execute.
